## 1. 배경 & 목표

### 1.1 왜 만드는가
지금 지라를 쓰고 있지만, 실제로 사용하는 기능은 **스프린트 운영, 태스크/에픽 관리** 정도로 한정적이다. 그에 비해 라이선스 비용, UI 무거움, 학습 곡선, 노션·깃헙과의 어색한 연계 등 비효율이 크다. **우리 워크플로우에 딱 맞는 가벼운 도구**를 만들어, 회의(스프린트 계획/회고)와 일일 업무 흐름을 더 매끄럽게 한다.

도구 이름은 **Slate** — 빈 슬레이트(slate)처럼 매 스프린트가 깨끗한 보드에서 시작해 차곡차곡 채워지는 느낌. 슬랙 봇 이름도 동일.

### 1.2 목표 (1단계 MVP 기준)
- 2주 단위 스프린트 사이클(계획 → 진행 → 회고)을 한 화면에서 운영할 수 있다.
- 여러 프로젝트를 독립적으로 운영할 수 있다 (각자 키/스프린트/보드 보유).
- 이슈를 빠르게 등록하고, 에픽으로 그룹핑할 수 있다.
- 칸반 보드에서 상태를 한눈에 본다.
- 깃헙 PR과 이슈가 양방향으로 엮인다 (커밋·PR 자동 링크, PR 머지 시 자동 Done).
- 이슈 변경이 슬랙 채널에 실시간으로 전달된다.
- 노션에 이슈 URL을 붙이면 `[ABC-123] 타이틀` 형태로 자동 미리보기가 뜬다. *(2단계로 이동 — 로컬 호스팅 결정으로 인해)*
- 기존 지라의 활성 이슈와 에픽을 가져와 새 도구에서 그대로 이어갈 수 있다.

### 1.3 비목표 (이 도구가 안 다루는 영역)
- 위키/문서 작성 (노션이 담당)
- 디자인/스토리보드 (피그마가 담당)
- 채팅/알림 허브 (슬랙이 담당)
- 복잡한 권한·승인 워크플로우, 커스텀 워크플로우 빌더
- 모바일 네이티브 앱 (모바일 반응형 웹까지만)

### 1.4 성공 기준
- 1단계 출시 후 4주 내 팀 100% 사용 전환 (지라 사용 중단)
- 스프린트 계획 회의 시간 30% 단축
- "노션에 링크 붙였을 때 미리보기 안 떠서 불편" 같은 불만 0건

## 2. 사용자 & 사용 시나리오

### 2.1 사용자 유형
| 유형 | 설명 | 권한 (1단계) |
|---|---|---|
| Member | 일반 팀원. 대부분의 사용자 | 이슈 CRUD, 스프린트 조회, 보드 사용 |
| Admin | 스프린트 생성/마감, 사용자 초대 | Member 권한 + 스프린트/프로젝트 설정 |

> 1단계에서는 권한을 이 두 단계로 단순화. 20명 넘어가면 권한 모델 재검토 (2단계 백로그).

### 2.2 주요 시나리오

**시나리오 A — 스프린트 계획 회의 (격주 월요일)**
1. Admin이 새 스프린트를 만든다 (기간 2주 자동 설정).
2. 팀원들이 백로그에서 이슈를 골라 스프린트에 드래그한다.
3. 각 이슈에 담당자와 (선택) 스토리 포인트를 매긴다.
4. 합산 포인트로 capacity 가늠.

**시나리오 B — 데일리 (매일 아침)**
1. 보드 뷰 열기 → 본인 카드 위주로 상태 갱신.
2. PR 올린 카드는 깃헙 연동으로 자동 In Review.

**시나리오 C — 이슈 등록 & 노션 연결**
1. 회의 중 "이거 이슈 만들자" → 새 이슈 등록 (제목·에픽·담당자만 빠르게).
2. 회의록(노션)에 이슈 URL 붙여넣기 → 자동으로 `[BBO-42] 로그인 버그 수정` 미리보기.

**시나리오 D — 스프린트 회고 (격주 금요일)**
1. 스프린트 리포트 화면 열기 → 완료 이슈, 미완료 이슈, 벨로시티 확인.
2. 미완료 이슈는 다음 스프린트로 이동 또는 백로그로 반환.

**시나리오 E — 깃헙에서 작업하면서**
1. 브랜치 이름 또는 커밋 메시지에 `BBO-42` 포함 → 이슈 페이지에 PR 링크 자동 표시.
2. PR 머지 → 이슈 상태 자동 Done.

## 3. 기능 명세

### 3.1 이슈 관리

**이슈 기본 필드**
| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| 키 | 문자열 (자동, 예: `DOTOLI-42`) | ✓ | 프로젝트 코드 + 일련번호. 1부터 자연 증가, 0 패딩 없음 (`DOTOLI-1`, `DOTOLI-42`, `DOTOLI-1000`). 영구 불변. |
| 제목 | 텍스트 | ✓ | |
| 본문 | Markdown | | 코드 블록, 이미지 첨부 지원 |
| 타입 | enum: Story / Task / Bug / Epic | ✓ | 기본값: Task |
| 상태 | enum: To Do / In Progress / In Review / Done | ✓ | 기본값: To Do |
| 담당자 | User (단일) | | 없음 허용 |
| 보고자 | User | ✓ | 자동: 생성자 |
| 에픽 | Issue (Epic 타입만) | | 부모 에픽 |
| 스프린트 | Sprint | | 미지정 시 백로그 |
| 우선순위 | enum: Highest / High / Medium / Low / Lowest | | 기본값: Medium |
| 스토리 포인트 | 정수 (0, 1, 2, 3, 5, 8, 13) | | 피보나치 권장 |
| 라벨 | 문자열 배열 | | 자유 입력, 자동완성 |
| 마감일 | 날짜 | | |
| 첨부파일 | 파일 배열 | | S3 등 오브젝트 스토리지 |
| 생성일/수정일 | 타임스탬프 | ✓ | 자동 |

**이슈 동작**
- 빠른 생성: 보드/백로그에서 인라인으로 제목만 입력해 생성 (그 외 필드는 나중에)
- 상세 페이지: 좌측 본문/코멘트, 우측 메타 필드, 하단 활동 로그
- 이슈 간 연결: `relates to`, `blocks`, `blocked by`, `duplicates` — UI는 가볍게 (드롭다운 + 링크 표시)
- 코멘트: Markdown, `@멘션`, 수정/삭제 (본인 코멘트만)
- 활동 로그: 모든 필드 변경 이력 (누가 언제 무엇을 → 무엇으로)

### 3.2 에픽

- 일반 이슈와 같은 엔티티지만 `type = Epic`
- 에픽 페이지: 소속 이슈 목록, 진행률(완료 이슈 수 / 전체), 간단한 요약
- 색상 라벨 지정 가능 (보드에서 카드 상단 컬러바로 표시)

### 3.3 스프린트

**스프린트 객체**
| 필드 | 설명 |
|---|---|
| 이름 | 자동: `Sprint 23 (06/01 - 06/14)` 또는 수동 |
| 시작일 / 종료일 | 기본 2주, 변경 가능 |
| 상태 | Planned / Active / Completed |
| 목표 | 자유 텍스트 (회고 때 참조) |

**동작**
- 동시에 Active 상태 스프린트는 1개만 (단순화)
- 스프린트 시작: Admin 클릭 → Planned → Active 전환
- 스프린트 마감: Active → Completed
  - 미완료 이슈 처리: "다음 스프린트로 이동" / "백로그로 반환" / "유지" 선택
- 자동 생성 옵션: 현재 스프린트 마감 시 다음 스프린트(2주) 자동 생성 토글

### 3.4 보드 (칸반)

- 컬럼: To Do / In Progress / In Review / Done (1단계는 고정)
- 카드 표시: 키, 제목, 타입 아이콘, 담당자 아바타, 포인트, 에픽 컬러바
- 드래그 앤 드롭으로 상태 변경
- 필터: 담당자, 에픽, 라벨, 텍스트 검색
- 스윔레인 토글: 없음 / 담당자별 / 에픽별
- 디폴트 뷰: 현재 Active 스프린트

### 3.5 백로그

- Active 스프린트와 백로그를 한 화면에 위아래로 배치
- 이슈를 위/아래로 드래그해서 스프린트에 넣고 빼기
- 스프린트 상단에 합산 포인트 표시 (`12 / 25 pt`)
- 백로그에서 새 이슈 빠르게 생성

### 3.6 스프린트 리포트

- 완료된 스프린트 별로 자동 생성
- 표시 내용:
  - 스프린트 목표
  - 계획 vs 실제 (계획한 이슈 수/포인트, 완료된 이슈 수/포인트)
  - 완료 이슈 리스트
  - 미완료 이슈 리스트 (어디로 갔는지 표시)
  - **벨로시티 차트**: 최근 5개 스프린트의 완료 포인트 막대그래프
- 회고 회의 화면용으로 큰 글씨/큰 표 모드 토글

### 3.7 검색 & 필터

- 글로벌 검색 (`Cmd/Ctrl + K`): 키, 제목, 본문, 코멘트 전문 검색
- 페이지별 필터: 담당자, 상태, 타입, 에픽, 라벨, 스프린트
- 저장된 필터 ("내 할일", "이번 스프린트 버그" 등) — 사용자별 저장
- 1단계는 JQL 같은 쿼리 언어 없음. 필터 UI만.

### 3.8 알림

**인앱 알림 (벨 아이콘)**
- 받는 이벤트: @멘션, 담당자 지정, 본인 이슈에 코멘트, 본인 보고 이슈의 상태 변경
- 읽음/안읽음 토글, 일괄 읽음 처리

**이메일 알림**
- 디폴트 OFF, 사용자 설정에서 ON 가능 (인앱 알림과 동일한 이벤트)

**슬랙 알림 (1단계 필수)**
- **단일 통합 채널**: 워크스페이스 설정에서 **알림 채널 1개**를 지정. 모든 프로젝트의 이슈 변경 알림이 이 채널로 모인다 (지금 지라가 하는 방식 그대로).
  - 메시지에 프로젝트 키(`[BBO-42]`, `[PAY-9]`)가 포함돼 있어 채널 안에서 프로젝트 구분 가능.
  - 프로젝트별로 별도 채널을 쓰고 싶어지면 2단계에서 추가 (프로젝트 설정에 채널 오버라이드 필드 자리만 비워둠).
- **알림 대상 이벤트** (이슈 변경 전체):
  - 이슈 생성 / 삭제
  - 상태 변경
  - 담당자 변경
  - 스프린트 이동 (백로그 → 스프린트, 스프린트 → 백로그, 스프린트 간 이동)
  - 에픽 변경
  - 우선순위 변경
  - 코멘트 추가
  - PR 연결 / 머지 (깃헙 연동 이벤트)
- **메시지 포맷** (예시):
  ```
  ◆ Slate · [DOTOLI-42] 로그인 버그 수정
  진주 → 상태 변경: In Progress → In Review
  담당: @bingo · 에픽: 인증 개편
  https://slate.bbodek.local/i/DOTOLI-42
  ```
  - 슬랙 Block Kit으로 키·제목 헤더, 변경 내용 본문, 링크 버튼 구성
  - **변경 1건 = 메시지 1개**. 묶거나 스레드로 잇지 않고 매번 새 메시지로 발송 (현재 지라 운영 방식 유지). 묶기/스레딩은 2단계 백로그.
- **노이즈 제어**:
  - 이슈 단위로 채널을 오버라이드할 수 있는 라벨 (예: `#slack:bbo-bugs`) — 1단계는 단순하게 라벨 매칭으로
  - 사용자 단위 mute (특정 이슈 채널 알림 끄기)는 2단계
- **봇 설치**: Admin이 슬랙 워크스페이스에 봇 앱 설치 (OAuth) → 통합 알림 채널 1개 선택 → 봇 초대
- **DM 알림 없음**: 본인이 담당자/멘션 받았어도 슬랙 DM은 보내지 않음. 통합 채널 알림 + 인앱 알림으로만 충분 (확정)
- **장애 대응**: 슬랙 전송 실패 시 재시도 큐 3회, 최종 실패는 Admin에게 인앱 알림

> 슬랙 알림은 1단계 핵심 기능으로 승격됨. 이슈 변경 = 슬랙 알림이 기본 동작.

### 3.9 인증 & 사용자

- 로그인: Google OAuth (회사 도메인 `@bbodek.com`만 허용)
- 첫 로그인 시 Member로 자동 가입
- Admin 지정은 기존 Admin이 사용자 관리 화면에서 토글
- 비활성화된 사용자는 로그인 불가, 할당된 이슈는 유지 (담당자만 자동 해제)

### 3.10 프로젝트 (다중 프로젝트)

**개념**
- 모든 데이터(이슈/스프린트/에픽/라벨)는 단일 프로젝트에 속한다.
- 한 사용자는 여러 프로젝트에 참여할 수 있다 (모든 프로젝트 디폴트로 조회 가능, 권한 분리는 2단계).
- 스프린트는 프로젝트별로 독립 운영 (프로젝트 A의 스프린트와 B의 스프린트는 별개).

**프로젝트 필드**
| 필드 | 설명 |
|---|---|
| 키 | 영문 2~5자 대문자 (예: `BBO`, `PAY`, `OPS`). 영구 불변. 이슈 키 접두어가 됨. |
| 이름 | 표시용 (예: "결제 시스템") |
| 색상/아이콘 | 사이드바·보드에서 구분용 |
| 깃헙 리포 연결 | 0개 이상 (한 프로젝트가 여러 리포 가능) |
| 자동 스프린트 생성 | 토글 (기본 ON) |
| 자동 상태 전환 룰 | 토글 (PR 머지 → Done 등) |

**프로젝트 동작**
- Admin이 새 프로젝트 생성 (키·이름 입력 → 색상 선택 → 깃헙 리포 연결). 슬랙 알림은 워크스페이스 공통 채널로 자동 전송됨.
- 키 충돌 방지 (전역 유일)
- 프로젝트 아카이브 가능 (읽기 전용 상태로 보존, 새 이슈 생성 차단)
- 프로젝트 삭제는 Admin + 추가 확인 (이슈 키 재사용 방지 위해 키는 영구 예약)
- 사이드바 상단에 **프로젝트 스위처** (드롭다운 또는 즐겨찾기 핀)
- "전체 보기" 모드: 본인 담당 이슈 등 일부 화면은 프로젝트 가로지르기

**프로젝트 간 동작**
- 이슈는 다른 프로젝트로 이동 가능 (키 변경됨, 활동 로그에 원래 키 기록, 기존 URL은 새 키로 영구 리디렉트)
- 에픽은 다른 프로젝트의 이슈를 자식으로 가질 수 없음 (1단계 단순화)
- 검색은 디폴트로 현재 프로젝트 범위, 토글로 전체 프로젝트 확장 가능

## 4. 통합 (Integration)

### 4.1 깃헙 연동

**1단계 — 자동 링크 (필수)**
- 깃헙 Webhook 등록: `push`, `pull_request` 이벤트 수신
- 수신 endpoint: **Supabase Edge Function** (`https://<project>.supabase.co/functions/v1/github-webhook`)
- 커밋 메시지 또는 PR 제목/본문/브랜치명에서 이슈 키 패턴(`[A-Z]+-\d+`, 예: `DOTOLI-42`) 검출
- 검출되면 해당 이슈 페이지에 자동 표시:
  - 연결된 커밋 (SHA, 메시지, 작성자, 시각)
  - 연결된 PR (번호, 제목, 상태 아이콘, 작성자)
- 이슈 페이지에서 PR로 가는 링크 표시 (역방향은 깃헙 UI에 댓글로 백링크 — 선택)

**2단계 — 상태 자동 전환 (필수)**
- PR이 `opened` & 이슈에 연결됨 → 이슈 상태가 `To Do`면 `In Review`로 변경
  - 이미 `In Progress`거나 `Done`이면 강제 변경하지 않음 (사용자 의도 존중)
- PR이 `merged` & 이슈에 연결됨 → 이슈 상태 `Done`으로 변경
- PR이 `closed without merge` → 상태 변경 없음, 활동 로그에만 기록
- 자동 전환 룰은 프로젝트 설정에서 ON/OFF 가능

**설정 화면**
- Admin이 깃헙 리포 연결: 리포 URL + GitHub App 설치 or Personal Access Token
- 연결된 리포 목록 표시, 웹훅 동작 상태(최근 수신 시각) 표시

### 4.2 노션 언펄 (Unfurl)

> ⚠️ **현재 상태**: 1단계가 로컬 호스팅으로 결정되면서 노션 언펄은 **2단계(공개 호스팅 이전 시)**로 이동. 아래 사양은 그때 그대로 적용 가능하도록 보존.

**요구사항**
- 노션은 링크 붙여넣기 시 해당 URL의 Open Graph 메타 태그를 읽어 미리보기를 표시한다.
- 따라서 이슈 상세 페이지(`https://tracker.bbodek.com/i/BBO-42`)는 **공개 접근 가능한 OG 메타 태그**를 가져야 한다.
- 단, 페이지 본문은 로그인된 사용자에게만 노출.

**구현 방식**
- 이슈 상세 페이지의 HTML `<head>`에 SSR로 다음 태그 삽입:
  - `<title>[BBO-42] 로그인 버그 수정</title>`
  - `<meta property="og:title" content="[BBO-42] 로그인 버그 수정">`
  - `<meta property="og:description" content="이슈 본문 앞 200자...">`
  - `<meta property="og:url" content="...">`
  - `<meta property="og:site_name" content="BBoDek Tracker">`
  - (선택) `<meta property="og:image">` — 에픽 컬러 + 상태 + 키가 들어간 동적 OG 이미지 (2단계)
- 비로그인 상태에서 이 페이지에 접근하면: `<head>`만 렌더하고 `<body>`는 로그인 안내 — 노션 크롤러는 OG만 읽으면 되니까 충분
- 이슈가 비공개로 설정된 경우(예: 보안 이슈) OG 노출 안 함 옵션 (2단계)

**검증**
- 출시 전 노션 페이지에서 실제 붙여넣기 테스트
- 슬랙·디스코드 등 다른 OG 소비자에서도 정상 동작 확인 (보너스)

### 4.3 슬랙 연동 (기술 사양)

> 사용자 관점 동작은 3.8을 참고. 여기서는 구현 사양만.

- 슬랙 앱 등록 (이름: **Slate**, OAuth scope: `chat:write`, `channels:read`, `groups:read`, `users:read`)
- 워크스페이스 단위로 단일 봇 토큰 + 단일 알림 채널 보관. 모든 프로젝트의 알림이 이 채널로 전송됨.
- 봇 토큰은 Supabase Vault에 암호화 저장.
- 발신 경로: **Postgres 트리거 → Edge Function → 슬랙 API**. 트리거 큐로 비동기 처리, rate limit 대응.
- 메시지 추적: 1단계는 묶기 안 함 (매번 새 메시지). `SlackMessage` 테이블은 추후 스레딩/리액션 동기화를 위해 자리만 잡아둠.
- 슬랙에서 봇 메시지에 이모지 리액션 → 인앱 활동 로그에 기록 (2단계 옵션).
- 슬랙 슬래시 커맨드 (`/tracker BBO-42`)로 이슈 요약 조회: 2단계.

### 4.4 지라 데이터 마이그레이션 (1단계 출시 전 실행)

**스코프 (어디까지 가져올지)**
- ✅ 프로젝트 메타 (키, 이름)
- ✅ 활성 이슈 + 활성 에픽 (status가 Done이 아닌 것 + 최근 3개월 내 종료된 것)
- ✅ 코멘트
- ✅ 라벨
- ✅ 첨부파일 (S3로 재업로드)
- ✅ 담당자 / 보고자 (이메일 매칭으로 사용자 연결)
- ✅ 이슈 키 보존 (`BBO-42`는 그대로 `BBO-42`로)
- ✅ 이슈 간 연결 (relates/blocks)
- ⚠️ 활동 로그: 마이그레이션 시점까지의 요약만 1줄로 ("Jira에서 가져옴, 종전 활동은 Jira 참조")
- ❌ 사용자 정의 필드 / 워크플로우 / 권한 / 와치 리스트
- ❌ 시간 추적, 워크로그
- ❌ 지라 자체 댓글 형식의 마크업은 마크다운으로 best-effort 변환 (실패하면 원문 보존)

**방식**
- 지라 REST API + 일회성 마이그레이션 스크립트 (CLI)
- 단계: Dry run → 검수 보고서 생성 → 본 마이그레이션 → 검증
- 이슈 키 충돌 방지: 마이그레이션 후 새 트래커의 이슈 키 카운터를 지라 최대값 + 1로 세팅 (예: 지라가 `BBO-487`까지 있으면 새 도구는 `BBO-488`부터)

**전환 방식 — 점진적 마이그레이션 (확정)**

한 번에 컷오버하지 않고, 1단계 도구가 완성되는 동안 **테스트하면서 점진적으로 옮긴다**.

- **Phase A — 테스트 단계 (도구 개발 중)**
  - 마이그레이션 스크립트가 dry run으로 동작
  - 일부 이슈만 옮겨와서 새 도구에서 잘 동작하는지 확인
  - 지라는 그대로 정상 운영
- **Phase B — 병행 운영**
  - 새 이슈는 새 도구에 등록 (DOTOLI 키 새로 발급)
  - 기존 지라 이슈는 그대로 지라에서 관리
  - 슬랙 알림은 양쪽 다 살아 있음 (잠시 시끄러움 감수)
- **Phase C — 본격 전환**
  - 활성 이슈/에픽을 일괄 이관
  - 지라 신규 등록 중단, 읽기 전용 전환
- **Phase D — 정리**
  - 지라 라이선스 해지 검토

> 따라서 별도 D-day 일정은 잡지 않음. 1단계 도구가 안정화되는 흐름에 맞춰 자연스럽게 전환.

**리디렉트**
- 1단계는 로컬 호스팅이라 외부 리디렉트는 의미 없음. 공개 호스팅 이전 시 재검토.
- 노션에 흩어진 기존 지라 링크는 그대로 유지 (지라가 살아 있는 동안 동작).

## 6. 화면 구성

핵심 화면 8개:

1. **로그인** — Google OAuth 버튼 한 개.
2. **프로젝트 스위처 / 홈** — 사용자가 참여 중인 프로젝트 카드 리스트. "전체 보기"에서는 본인 담당 이슈 통합 뷰.
3. **보드** (프로젝트 디폴트) — 현재 Active 스프린트의 칸반.
4. **백로그** — 백로그 + Active 스프린트 위아래 분할.
5. **이슈 상세** (`/i/BBO-42`) — 좌: 본문/코멘트/활동, 우: 메타 필드, 하단: 깃헙 링크 + 슬랙 알림 미리보기.
6. **에픽 상세** — 일반 이슈 상세 + 소속 이슈 목록 + 진행률.
7. **스프린트 리포트** — 완료된 스프린트별 요약 + 벨로시티 차트.
8. **설정**
   - 워크스페이스 설정: 사용자 관리, 슬랙 워크스페이스 연결 + 통합 알림 채널 1개 지정, 마이그레이션 도구 (Admin)
   - 프로젝트 설정: 키/이름/색상, 깃헙 리포 연결, 자동화 룰, 라벨 관리, 아카이브
   - 개인 설정: 알림 채널 (인앱/이메일), 단축키

추가:
- 글로벌 네비: 좌측 사이드바 상단에 **프로젝트 스위처** (현재 선택된 프로젝트 표시 + 드롭다운으로 전환). 그 아래 보드 / 백로그 / 에픽 / 리포트 / 설정.

- 우측 알림 벨 + 프로필.
- 빠른 이슈 생성 모달: 어디서든 `C` 단축키로 호출. 첫 줄에 프로젝트 선택.

## 7. 비기능 요구사항

- **아키텍처 (확정)**:
  - **프론트엔드**: 1단계는 로컬/사내 머신에서 Docker Compose로 띄움. 2단계에서 Vercel 등 공개 호스팅으로 이전.
  - **백엔드**: **Supabase Cloud** — Postgres DB + Auth(Google OAuth) + Storage(보조용) + Realtime + Edge Functions.
  - **첨부파일**: AWS S3 (사내 기존 자산). Supabase Storage는 보조용.
  - **웹훅 수신 (깃헙)**: **Supabase Edge Functions** 가 공개 URL을 제공하므로 별도 터널링 불필요. 깃헙 웹훅 → Edge Function → Postgres에 직접 기록.
  - **슬랙 발신**: Edge Function 또는 백그라운드 잡으로 Supabase에서 직접 발신.
- **데이터 위치**: 이슈/사용자 데이터는 Supabase 인프라 (리전: ap-northeast-2 서울 권장). 첨부파일은 사내 S3.
- **개발 환경**: 로컬에서 Supabase CLI로 마이그레이션 관리, `supabase start`로 로컬 인스턴스도 띄울 수 있음.
- **성능**: 이슈 1만 건 기준 보드 로딩 1초 이내, 검색 결과 500ms 이내.
- **반응형**: 데스크탑 우선, 태블릿/모바일은 읽기·간단한 상태 변경까지만 지원.
- **접근성**: WCAG AA 수준 (키보드 네비, 색약 대응, 단축키 안내).
- **국제화**: 한국어 only로 시작. i18n 구조만 잡아둠.
- **데이터 백업**: DB 일 1회 스냅샷, 30일 보관. (로컬 호스팅 단계에서는 호스트 머신 백업 정책에 의존)
- **로그**: 모든 쓰기 액션 활동 로그에 기록, 90일 보관.
- **감사 / 보안**: 회사 도메인 외 가입 차단(공개 호스팅 시), 세션 만료 14일, 깃헙·슬랙 토큰은 암호화 저장.
- **첨부파일 스토리지**: **AWS S3** (사내 기존 자산 활용). presigned URL 방식으로 직접 업로드/다운로드. 버킷 1개, 키 prefix로 환경/프로젝트 구분.
- **외부 연동 (Supabase Cloud + Edge Functions 기반)**:
  - **깃헙 웹훅 수신**: Edge Function이 제공하는 공개 URL을 깃헙 웹훅 endpoint로 등록. 별도 터널링 불필요. ✓
  - **슬랙 발신**: Edge Function에서 직접 발송. ✓
  - **노션 언펄**: 프론트엔드가 1단계에서 로컬에 있어 외부 크롤링 불가 → 2단계 공개 호스팅 이전 시 부활.

## 8. 로드맵

### 1단계 — MVP (로컬 환경 출시 목표)
**다중 프로젝트** 지원 (초기 `DOTOLI` 1개), 이슈 CRUD, 에픽, 스프린트 운영, 칸반 보드, 백로그, 스프린트 리포트(벨로시티 포함), 코멘트, 활동 로그, 라벨, 마감일, 우선순위, 이슈 연결, 검색/필터, Google OAuth, 깃헙 연동(자동 링크 + PR 머지 시 자동 Done), 인앱 알림, **슬랙 알림(이슈 변경 전체, 단일 통합 채널, 매번 발송)**, **지라 데이터 점진적 마이그레이션 도구**.

### 2단계 (공개 호스팅 이전 + 확장)
**공개 클라우드 배포**, **노션 OG 언펄**, 동적 OG 이미지, 번다운 차트, 저장된 필터 공유, 모바일 반응형 강화, 비공개 이슈, 첨부파일 큰 용량 지원, 이슈 템플릿, 슬랙 리액션 동기화, 슬랙 슬래시 커맨드, 프로젝트별 슬랙 채널 오버라이드, 사용자 단위 알림 mute.

### 백로그 (시급하지 않음)
JQL 같은 쿼리 언어, 커스텀 필드, 커스텀 워크플로우, 시간 추적, 권한 모델 확장 (프로젝트별 권한), API 공개, 모바일 앱.

## 9. 미정 사항

v1.0 잠금 시점 기준 1단계 진입에 필요한 모든 핵심 결정이 완료됨. 아래는 **개발하면서 자연스럽게 결정될 잔여 항목**.

**v1.0 확정 항목 (전체 합본)**
- ✅ **도구·봇 이름**: **Slate** (빈 슬레이트 — 깨끗한 보드)
- ✅ **백엔드**: **Supabase Cloud** (Postgres + Auth + Storage + Realtime + Edge Functions, 리전 ap-northeast-2)
- ✅ **첨부파일 스토리지**: **AWS S3** (사내 기존 자산)
- ✅ **깃헙 웹훅 수신**: **Supabase Edge Functions** 공개 URL (별도 터널링 불필요)
- ✅ **다중 프로젝트** 지원, 첫 시드 프로젝트 `DOTOLI` 1개로 테스트
- ✅ **이슈 키**: `DOTOLI-1` 자연 증가, 0 패딩 없음
- ✅ **슬랙 알림**: 단일 통합 채널, 이슈 변경 전체, 변경 1건 = 메시지 1개, DM 없음
- ✅ **지라 마이그레이션**: 점진적 (D-day 없음). Phase A→B→C→D 흐름
- ✅ **1단계 호스팅**: 프론트엔드 로컬 + 백엔드 Supabase Cloud
- ✅ **노션 언펄**: 2단계 (프론트엔드 공개 호스팅 이전 시 부활)
- ✅ **인증**: Google OAuth (회사 도메인 한정). 권한 Member/Admin 2단계.

**개발 중 결정 항목**
1. **슬랙 봇 아이콘 이미지** — 슬레이트(석판) 모티프 또는 ◆ 다이아몬드 아이콘 일러스트 권장 (단순·식별성).
2. **마이그레이션 대상 범위** — 점진적으로 옮기면서 조정 (활성 이슈 우선, 종료 이슈는 필요 시).
3. **지라 사용자 매핑 예외 케이스** — 퇴사자/이메일 변경 등은 dry run 단계에서 1:1 처리.
4. **회고 전용 모드** — 사용해보고 필요하면 2단계에 추가.
5. **"전체 보기" 통합 뷰 범위** — 두 번째 프로젝트 생기는 시점에 결정.
6. **국제화 (i18n)** — 1단계는 한국어 only, 구조만 잡아둠.
